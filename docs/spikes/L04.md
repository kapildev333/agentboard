# L04 spike: Claude Code hook injection, session ids, resume

Claude Code 2.1.309, macOS, Node 22.11. Every run used a fresh `--session-id`, a scratch directory under the worktree (deleted afterwards), never `--dangerously-skip-permissions`. Hooks were caught by a throwaway Node listener on a random free port that logged each POST's path, `X-AgentBoard-Token` header and JSON body; it was stopped by the PID listening on that port.

Launch args came from `claudeLaunch()` in `packages/daemon/src/agents/claude/index.ts`:

```
claude --session-id <uuid> --name <name> --settings '{"hooks":{"Stop":[{"hooks":[{"type":"http","url":"<daemonUrl>/hook/<consoleId>","headers":{"X-AgentBoard-Token":"<token>"},"timeout":5}]}], ...same for Notification, UserPromptSubmit, PermissionRequest, SessionEnd}}'
```

## Run 1: inline hooks reach the daemon

`claude <args> -p "Reply with just the word hi."` printed `hi` and exited 0. The listener got, in order, `UserPromptSubmit`, `Stop` and `SessionEnd` (reason `other`), all on `/hook/<consoleId>` with the token header. Every body's `session_id` equals the id passed to `--session-id`. The bodies also carry `transcript_path`, `cwd`, `prompt_id`, `permission_mode`, and `session_title` (the `--name` value). So the daemon can check the session id against the console's.

## (1) Do inline `--settings` hooks merge or replace? They merge.

- **User level (temporary `CLAUDE_CONFIG_DIR`):** a fresh config dir with a `settings.json` holding a user Stop hook and a user SessionEnd hook, each a `command` hook that appends a marker line. The real `~/.claude` was not touched. That config dir has no login, so the run ended with "Not logged in" and no model turn, which means Stop never fired. SessionEnd did fire, and both hooks ran: the marker file got `user-end` and the listener got `SessionEnd` (plus `UserPromptSubmit`). User-level and inline hooks for the same event both run.
- **Project level plus plugin plus inline, logged in:** in the scratch dir, `.claude/settings.json` had a project Stop `command` hook. The launch added `--plugin-dir packages/plugins/claude-hooks` with `AGENTBOARD_CONSOLE_ID=c-plugin` on top of the inline settings for `c-inline`. Stop fired from all three sources: the marker got `project-stop`, and the listener got `UserPromptSubmit`, `Stop` and `SessionEnd` for both `/hook/c-inline` and `/hook/c-plugin`.
- The user's installed plugins (superpowers, ponytail, ui-ux-pro-max) stayed enabled in these runs. Nothing about `--settings` turns them off.

Hooks combine per event across sources. `--settings` adds hooks; it does not replace the user's.

## (2) Does `--session-id` let the daemon resume later? Yes.

After run 1, `claude --resume <same id> --name ... --settings ... -p "What exact word did you reply with in your previous message? ..."` answered `hi`. The hooks for the resumed run (`UserPromptSubmit`, `Stop`, `SessionEnd`) carried the same `session_id`. Only one transcript file exists, `~/.claude/projects/<dir>/<id>.jsonl`. Resume keeps the id and does not fork, so the id the daemon stores at spawn stays valid across any number of resumes. Resume was only tested from the same directory it started in.

## (3) Which notifications arrive, and what does PermissionRequest look like?

These runs were interactive: claude ran in a node-pty PTY with the prompt "Use the Bash tool to run exactly this command: touch perm-probe.txt".

- **First run, permission mode inherited:** the session came up in auto mode and ran `touch` without asking. The hooks were `UserPromptSubmit`, then `Stop`, then `Notification` with `notification_type: "idle_prompt"` and message "Claude is waiting for your input" within 90 s of Stop. The 60 s idle threshold comes from the hooks documentation; this run did not time it, then `SessionEnd` with reason `prompt_input_exit` after `/exit`.
- **Second run, `--permission-mode default`:** the run got `UserPromptSubmit` and, about 3 s in, `PermissionRequest` and then `Notification` with `notification_type: "permission_prompt"` and message "Claude needs your permission". Pressing Escape to deny produced **no Stop** and **no idle_prompt** in the next 90 s. After `/exit` came `SessionEnd` with reason `prompt_input_exit`.

Only `permission_prompt` and `idle_prompt` were observed. The rest of this paragraph comes from the docs, not a run. Claude Code's hooks documentation lists the Notification matcher values `permission_prompt`, `idle_prompt`, `auth_success` and `elicitation_dialog`, and the spec's status row also names `agent_needs_input`. L13 must accept all five. It should map `permission_prompt`, `elicitation_dialog` and `agent_needs_input` to needs you, map `idle_prompt` to idle, ignore `auth_success`, and ignore any unknown type rather than fail.

PermissionRequest body (paths redacted):

```json
{
  "session_id": "9c8991f2-...",
  "transcript_path": "<transcript>",
  "cwd": "<cwd>",
  "scratchpad_dir": "<tmp>/scratchpad",
  "prompt_id": "f74d5f28-...",
  "permission_mode": "default",
  "effort": { "level": "high" },
  "hook_event_name": "PermissionRequest",
  "tool_name": "Bash",
  "tool_input": { "command": "touch perm-probe.txt", "description": "Create empty probe file" },
  "permission_suggestions": [
    { "type": "addDirectories", "directories": ["<cwd>"], "destination": "session" },
    { "type": "setMode", "mode": "acceptEdits", "destination": "session" }
  ]
}
```

What this means for L13:
- PermissionRequest comes first and the `permission_prompt` Notification follows, so either one can mark "needs you".
- After a denial or interrupt, no Stop arrives. The console stays "needs you" until the next `UserPromptSubmit`, unless the quiet timer moves it to idle.
- From the docs, not a run (the listener always answered `{}`): the HTTP response to PermissionRequest can decide the prompt, so `/hook` must answer `{}` or an empty 2xx body and never a decision.

## Token in a header from the environment

A separate `-p` run used the header `"X-AgentBoard-Token": "$AGENTBOARD_TOKEN"` with `"allowedEnvVars": ["AGENTBOARD_TOKEN"]` and `AGENTBOARD_TOKEN=from-env` set in the environment. The listener got `from-env`. So the token can stay out of argv, where `ps` shows it.

## (4) Recommendation for L14: inline `--settings`

Both routes merge with the user's hooks, so the deciding factors are these:
- Inline settings need nothing on disk and no runtime besides claude. Each console gets its own URL and console id in its own args, and there's no plugin path to resolve or ship.
- `--plugin-dir` needs the plugin folder on disk and `node` on PATH, and it starts a process per hook event. That is extra latency and one more failure point. It fits the case where a plain `claude` the board did not launch should still report status (L25), not the case where the board starts claude itself.
- Neither route touches `~/.claude/settings.json`, which is what F2.2 requires.

For L14, use the env form of the header (`$AGENTBOARD_TOKEN` plus `allowedEnvVars`) and set `AGENTBOARD_TOKEN` in the PTY env, so the token never appears in `ps`. One catch, from the docs and not tested here: if any settings source defines `httpHookAllowedEnvVars` and leaves `AGENTBOARD_TOKEN` out, the header comes out empty, so L14 should check for that or fall back to the inline token. `claudeLaunch` puts the token straight into the header today because the card fixes its return value as `{ command, args }` with no env.
