# L06 spike: Codex notify and Gemini hooks per launch

Code: `packages/daemon/src/agents/{codex,gemini}/index.ts`, `packages/daemon/src/agents/notify-relay.ts`.

## Codex

- **Installed here:** the npm package `@openai/codex` 0.53.0 is on PATH (`/usr/local/bin/codex`), but the binary is killed on launch in this sandbox (exit 137, no output), so nothing below was run live. Evidence is `strings` on the shipped binary (it contains `agent-turn-complete`, `thread-id`, `turn-id`, `input-messages`, `last-assistant-message`, `CODEX_HOME`, "Failed to resume session from") plus Codex's documentation. **Verify live on a machine where it runs** (see "To verify").
- **Per-launch hook:** yes. Any `config.toml` key can be overridden with `-c key=value` (value parsed as TOML). `codexLaunch` passes `-c 'notify=["node","<abs>/notify-relay.js"]'`. `CODEX_HOME=<dir>` with a generated `config.toml` is the fallback, but it moves auth and sessions too, so `-c` is preferred. No edit to `~/.codex` is needed; the opt-in config edit (F2.2) is not required for Codex.
- **Resume:** `codex resume <SESSION_ID>` (also `codex resume --last`). `-c` still works after it.
- **Session id:** Codex cannot be told an id at start. It writes `$CODEX_HOME/sessions/YYYY/MM/DD/rollout-<timestamp>-<uuid>.jsonl` (default `~/.codex/sessions`); the uuid is the id and the first JSONL line (`session_meta`) repeats it with `cwd`. The notify payload carries it as `thread-id`.
- **Event:** only one, `agent-turn-complete`. Codex runs the program with the JSON as the **last argv argument** (not stdin), environment inherited:
  `{"type":"agent-turn-complete","thread-id":"<uuid>","turn-id":"<str>","cwd":"<abs>","input-messages":["..."],"last-assistant-message":"..."}`
  (`cwd` is present in recent versions; treat as optional.)
- **Not covered:** no event on turn start, on approval request or on exit. "working" and "needs you" stay on output matching and PTY exit, as the spec table says.

## Gemini CLI

- **Installed here:** no (`which gemini` empty). Everything below is from documentation already in context, not run. **Verify live.**
- **Per-launch hook:** yes, probably. Settings merge from defaults, user `~/.gemini/settings.json`, project `.gemini/settings.json`, and a system file whose path `GEMINI_CLI_SYSTEM_SETTINGS_PATH` overrides. `geminiLaunch` writes `<tmpdir>/agentboard/<consoleId>/gemini-settings.json` (0600) with `hooks` for `BeforeAgent`, `AfterAgent`, `Notification` and sets that variable. Caveat: the system layer is highest precedence, so it can shadow an enterprise system file; acceptable on a personal machine. If the variable is not honoured, fall back to the opt-in one-time edit of `.gemini/settings.json` with a diff.
- **Hook config shape:** `{"hooks":{"AfterAgent":[{"hooks":[{"type":"command","command":"node /abs/notify-relay.js"}]}]}}`.
- **Resume:** `gemini --resume <session-id>` (`--resume latest` or an index also accepted; `--list-sessions` prints them).
- **Session id:** every hook payload has `session_id`; transcripts live in `~/.gemini/tmp/<project-hash>/chats/session-<timestamp>-<short-id>.json`. Gemini cannot be given an id at start, so capture it from the first hook payload (`BeforeAgent` fires at the first prompt) rather than from files.
- **Events and payload:** hooks receive JSON on **stdin**: `{"session_id","transcript_path","cwd","hook_event_name","timestamp", ...}` plus per event: `BeforeAgent`/`AfterAgent` add `prompt` (AfterAgent also `prompt_response`, `stop_hook_active`); `Notification` adds `notification_type` (for example `ToolPermission`), `message`, `details`. A hook must print JSON or nothing on stdout and exit 0 to not block.

## Relay

`notify-relay.js`: payload = `argv[2]` (Codex) else stdin (Gemini). POSTs the raw body to `$AGENTBOARD_URL/hook/$AGENTBOARD_CONSOLE_ID` with `authorization: Bearer $AGENTBOARD_TOKEN`, 2 s timeout, swallows every error, exit 0. The relay does not add the agent or event name: Codex payloads are identified by `type`, Gemini by `hook_event_name`.

## For L14

Call `codexLaunch` / `geminiLaunch` with `{consoleId, daemonUrl, token, sessionId?, resume?}`; spawn `command` with `args`, and merge `env` over the login-shell env. `resume` only takes effect together with `sessionId`. Neither CLI accepts a chosen id at start, so L14 must read the real id after spawn: Codex from the newest `rollout-*.jsonl` under `$CODEX_HOME/sessions` whose `cwd` matches (or the first notify `thread-id`), Gemini from the first hook's `session_id`; two consoles in one directory are told apart by spawn time and by claiming each id once. `geminiLaunch` writes a temp file per call; remove `<tmpdir>/agentboard/<consoleId>` on console exit. The relay path is resolved relative to the compiled `dist/agents/notify-relay.js`, so run the daemon from the build (or give L14 a `tsx`-aware path) or notifications silently do nothing. For L13: the hook route receives raw agent JSON, so the mapper keys on `type === "agent-turn-complete"` (Codex) or `hook_event_name` (Gemini).
