# L05 spike: OpenCode plugin events

Status of evidence. The governor ruled mid-lane that the `opencode` binary must not be run on this machine (macOS malware dialogs). Only `buildHookPost` and the plugin factory are proven here, by `packages/plugins/test/opencode.test.ts`. Everything about OpenCode itself below is **from documentation, not run here**, except the items marked *early run*: before the rule arrived, one throwaway run of opencode 1.19.4 (installed outside the repo, since deleted) against a fake OpenAI-compatible server was made. Treat those as unverified by the governor. The "real opencode on a local model fires all three events" done-criterion is therefore **not met**; no local model was available (no ollama) and the binary is now off limits. `permission.asked` and `tool.execute.before` were never observed firing.

## Session id and storage

- Sessions have ids like `ses_<hex>`. *Early run:* 1.19.4 stores them in SQLite, not JSON files: `$XDG_DATA_HOME/opencode/opencode.db` (default `~/.local/share/opencode/opencode.db`), table `session` (`id`, `project_id`, `directory`, ...), plus `message`, `part`, `permission`, `todo`. `opencode db path` prints the path. Older versions documented JSON under `~/.local/share/opencode/storage/session/<projectID>/<sessionID>.json`; L14 should not rely on it.
- `XDG_DATA_HOME`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME`, `XDG_CACHE_HOME` relocate all of it.

## Resume

- From `opencode --help` / `opencode run --help` *(early run)*: `opencode --session <id>` (`-s`) resumes a session in the TUI; `--continue` (`-c`) resumes the last one; `--fork` forks it. `opencode session list` lists sessions.
- Resume args for L14: `['--session', sessionId]`.

## Can the plugin learn its session id at session.created?

Yes in principle: `event` receives `session.created` with `properties.info.id` (documentation). *Early run:* `session.status` and `session.idle` payloads carry `properties.sessionID`, so the daemon can capture the id from the first hook it gets. The plugin currently forwards only the four types in the card; to capture the id earlier, L26 can add `session.created` to `WATCHED` in `hook.ts`. L13/L14 should treat `payload.sessionID` (or `payload.info.id` for `session.created`) as the resume id.

## Findings that change the design

1. **OpenCode calls every export of a plugin file as a plugin** *(early run)*. Exporting `buildHookPost` from `agentboard.ts` made it run as a plugin and return `null`, which broke the loader (`plugin config hook failed`). So the helper lives in `hook.ts` and `agentboard.ts` exports only `AgentBoard`.
2. **Every `.ts` file in a `plugins/` directory is loaded as a plugin** *(early run)*; `hook.ts` placed there logs "Plugin export is not a function". Do not copy the folder into `.opencode/plugins/`.
3. Events seen *(early run)* for one prompt: `session.status` busy (several), `session.status` idle, `session.idle`; delivered to `POST /hook/<id>` with `{agent, event, payload}`.

## For L14 and L26: launching opencode

- Ship the plugin directory (`agentboard.ts` + `hook.ts`) to a stable path such as `~/.agentboard/plugins/opencode/`, and load it per launch with the config-content env var rather than writing into the user's repo or global config: `OPENCODE_CONFIG_CONTENT='{"plugin":["file:///home/.../.agentboard/plugins/opencode/agentboard.ts"]}'` (documented; *not verified here*, the one run used it with no output because it was cut off). Fallback: a `plugin` entry in a generated config pointed to by `OPENCODE_CONFIG`.
- Environment for the child: `AGENTBOARD_URL=http://127.0.0.1:<port>`, `AGENTBOARD_CONSOLE_ID=<id>`. The plugin is inert when either is missing and never throws if the daemon is down.
- The hook route currently needs no token in this plugin; if L12 requires one on `/hook/:id`, add `AGENTBOARD_TOKEN` and a header to `buildHookPost` (request below).
- Status map for L13: `session.status` payload `status.type` is `busy` or `idle`; `session.idle` means the turn finished.
